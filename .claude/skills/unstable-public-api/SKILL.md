# 불안정한 공공 API 앞에서 앱을 지키기

이 문서는 medi365가 응급의료포털(E-Gen)로 하루종일 얻어맞으며 실측으로 확인한 것들이다.
추측이 아니라 관측 결과이므로, 여기 적힌 판단을 뒤집을 때는 반드시 재측정부터 한다.

핵심 전제 하나: **상류는 반드시 죽는다.** 죽지 않게 만들 수는 없으니, 죽었을 때
사용자가 빈 화면을 보지 않게 만드는 것이 전부다.

## 0. 먼저 우리 쪽 문제인지부터 배제한다

장애를 만나면 대응 코드를 짜기 전에 원인을 좁힌다. 아래 순서로 하면 30분 안에 끝난다.

| 확인 | 방법 | 판정 |
| --- | --- | --- |
| 포털 자체는 살아있나 | 포털 웹사이트(`www.data.go.kr`)에 HTTP 요청 | 200인데 API만 실패 → 상류 API 게이트웨이 장애 |
| 우리 IP만 막힌 건가 | 로컬 PC + 배포 환경(다른 국가/IP) 양쪽에서 호출 | 둘 다 실패 → IP 차단이 아니라 상대편 장애 |
| 파라미터 표기 문제인가 | 상류가 자기 데이터에서 쓰는 표기를 수집해 대조 | 일치하면 표기 문제 아님 |
| 응답 크기 문제인가 | `numOfRows`를 바꿔가며 **각 조건 8회씩** 측정 | 상관관계 없으면 노이즈. 1~2회 측정으로 결론 내지 말 것 |
| 트래픽 한도인가 | 오류 코드 확인 | 한도 초과는 별도 코드(예: `22`)로 온다. 연결실패(`05`)와 다르다 |

가장 흔한 함정은 **1~2회 관측으로 인과를 만드는 것**이다. 간헐 장애는 노이즈가 지배적이라
"numOfRows를 줄였더니 됐다" 같은 결론이 쉽게 나오고, 그 결론에 맞춰 짠 코드는 아무것도
고치지 못한 채 복잡도만 남긴다.

## 1. 오류를 캐시하면 장애가 고정된다 — 가장 비싼 함정

공공데이터포털 계열 API는 **오류를 `HTTP 200 + 오류 XML`로 내려준다.**
따라서 상태 코드만 보고 캐시하면 CDN이 오류를 정상 응답으로 알고 저장한다.
그러면 사용자가 '다시 시도'를 눌러도 캐시된 오류가 그대로 돌아오고,
**장애가 캐시 기간만큼 고정된다.** 캐시 시간을 늘려둔 상태였다면 피해가 그만큼 커진다.

본문의 결과 코드까지 확인한 뒤에만 캐시한다:

```js
// api/egen.js — 성공 응답만 캐시한다
const code = (body.match(/<resultCode>([^<]*)<|<returnReasonCode>([^<]*)</) || [])
  .slice(1).find(Boolean);
const cacheable = upstream.ok && (code === '00' || code === '0000');

res.setHeader(
  'cache-control',
  cacheable ? 's-maxage=300, stale-while-revalidate=600' : 'no-store',
);
```

catch 블록에서도 `no-store`를 붙인다. 예외 경로가 캐시 헤더 없이 빠져나가면
플랫폼 기본값이 무엇이든 그대로 적용된다.

**캐시해도 안전한지 판단하는 기준**: 캐시되는 것이 *사실 데이터*(기관 목록, 요일별
시간표)인지 *판정 결과*(지금 영업중인가)인지 본다. 판정을 클라이언트가 현재 시각으로
매번 계산한다면 목록을 5분 캐시해도 정확도에 영향이 없다. 판정까지 서버에서 구워
캐시하면 그 순간 캐시 시간만큼 틀린 답을 준다.

## 2. 재시도는 '일시적 실패'에만 건다

전부 재시도하면 인증 오류·잘못된 파라미터처럼 절대 성공하지 않을 요청에
지연만 3배로 붙는다. 한도 초과(`22`)에 재시도하면 한도를 더 태운다.

```js
function isTransient({ status, code }) {
  if (status && status >= 500) return true;          // 502 / 503 / 504
  return code === '01' || code === '04' || code === '05';
  // 01 어플리케이션 오류 · 04 HTTP 오류 · 05 서비스 연결실패/타임아웃
}
```

- 네트워크 예외(연결 실패, abort)도 일시적으로 본다.
- 백오프는 짧게. medi365는 `[400ms, 1200ms]` 2회다. 사용자가 화면 앞에서 기다리는
  중이므로 지수 백오프로 30초를 끄는 것은 실패보다 나쁘다.
- **효과 측정치**: 전국 21개 시군구 실측에서 재시도 도입만으로 성공 4/21 → 16/21.

## 3. 모든 호출에 시간 상한을 둔다

상한이 없으면 화면이 영원히 "검색 중"에 머문다. 실패보다 나쁜 상태다 —
사용자는 무엇을 해야 할지 알 수 없고, 재시도 버튼조차 못 누른다.

```js
const REQUEST_TIMEOUT_MS = 10_000;
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), REQUEST_TIMEOUT_MS);
try {
  res = await fetch(url, { signal: controller.signal });
} finally {
  clearTimeout(timer);
}
```

**콜백 기반 SDK는 더 위험하다.** 콜백이 오지 않으면 Promise가 영원히 매달리고
`AbortController`도 없다. 반드시 감싼다:

```js
function withTimeout(promise, fallback = null, ms = 8000) {
  return Promise.race([
    promise,
    new Promise((resolve) => setTimeout(() => resolve(fallback), ms)),
  ]);
}
```

## 4. 부분 실패는 조용한 0건이 되면 안 된다

여러 지역·여러 갈래를 동시에 조회할 때 `Promise.all`을 쓰면 하나만 실패해도
전부 버린다. `Promise.allSettled`로 받아 **성공한 만큼 보여주고, 실패를 알린다.**

```js
const results = await Promise.allSettled(jobs);
// ...성공분 병합, 실패 카운트...
// 전부 실패한 경우에만 에러를 올린다
if (merged.size === 0 && lastError) throw lastError;
return { items: [...merged.values()], failed, total: jobs.length };
```

그리고 UI에 반드시 남긴다:

> ⚠ 응급의료포털이 불안정해 일부 지역(3/21)을 불러오지 못했습니다.
> 결과가 실제보다 적을 수 있습니다.

이 문구가 없으면 "우리 동네엔 문 연 약국이 없구나"라는 **틀린 확신**을 준다.
의료·안전 도메인에서 조용한 누락은 오류보다 해롭다.

## 5. 폴백이 아니라 합집합, 그리고 정적 스냅샷

의존을 줄이는 순서는 이렇다.

1. **정적 데이터셋을 1순위로** — 하루 1회(또는 3시간 주기) 미리 받아 저장소에 커밋해
   배포한다. 상류가 죽어도 앱은 뜬다.
2. **API는 폴백이 아니라 합집합으로** 합친다. "정적이 없으면 API"로 짜면 정적 데이터의
   커버리지 판정 버그가 곧바로 조용한 누락이 된다. 둘 다 받아 고유 ID로 병합하는 편이
   덜 틀린다.
3. **최후 수단은 다른 제공자** — medi365는 E-Gen도 정적도 없을 때 카카오 장소검색으로
   주변 목록을 띄운다. 영업시간을 알 수 없으므로 **그 사실을 크게 경고**하고
   "방문 전 전화 확인"을 안내한다. 아무것도 못 보여주는 것보다 낫지만,
   **품질이 다르다는 것을 숨기면 안 된다.**

### 정적 스냅샷 파이프라인의 필수 안전장치

- **수집 실패 시 커밋하지 않는다.** 그래야 마지막 정상 데이터가 배포에 그대로 남는다.
  빈 파일을 커밋하면 상류 장애가 우리 배포 데이터까지 파괴한다.
- **신선도 가드**: 3시간마다 시도하되 데이터가 이미 N시간 이내면 아무것도 하지 않는다.
  평소엔 하루 한 번만 실제 수집하고, 장애 때는 3시간마다 복구를 따라잡는다.
- **동시 실행 방지**: 같은 파일을 건드리므로 `concurrency` 그룹으로 겹치지 않게 한다.

## 6. 인증키·프록시

- 브라우저 직접 호출은 CORS로 막히므로 서버 프록시를 둔다. 인증키는 **서버에서 주입**하고
  클라이언트가 보낸 `serviceKey`는 무시한다.
- 프록시가 아무 경로나 중계하면 오픈 프록시가 된다. 허용 접두사를 검사한다.
- 인증 오류는 재시도해도 소용없다. 메시지에 **다음 행동**을 적는다 —
  "Decoding 키가 들어갔는지, 해당 서비스 활용신청이 승인됐는지 확인하세요."
- `HTTP 404`는 대개 상류가 아니라 **우리 rewrite 설정이 배포에 반영되지 않은 것**이다.

## 7. 오류 메시지는 사용자 언어로, 다음 행동과 함께

내부 코드를 그대로 노출하지 않는다. 대신 원인 계열별로 문구를 나눈다.

| 상황 | 문구 |
| --- | --- |
| 일시적 장애 | "응급의료포털이 일시적으로 불안정합니다. 잠시 후 다시 시도해 주세요." + 재시도 버튼 |
| 타임아웃 | "응급의료포털이 응답하지 않습니다." |
| 부분 실패 | "일부 지역(3/21)을 불러오지 못했습니다. 결과가 실제보다 적을 수 있습니다." |
| 품질 저하 폴백 | "영업시간을 확인할 수 없습니다 — 방문 전 전화로 확인해 주세요." |
| 개발자용(인증 등) | 확인할 설정 이름을 그대로 적는다 |

재시도 버튼이 없는 오류 화면은 미완성이다. 간헐 장애는 대부분 한 번 더 누르면 된다.
